# Выбор исполнителя

Основное правило — в `~/.claude/CLAUDE.md`, раздел «Делегирование»: простое по умолчанию в agy Flash. Скилл нужен только для спорных случаев. Не менять модель основной сессии посреди работы.

## 1. Карточка (пишет основная модель, 5 строк)

- Файлы: сколько и какие.
- Эталон: есть похожий готовый код / нет.
- Новое состояние или логика: да / нет.
- Важность: важный код, дизайн, тексты сайта, опорная документация / нет. Режим: /orc или /super-orc / обычная сессия.
- Воспроизводимость: ясные шаги / плавающий баг.

## 2. `jev_classify` — один item, текст = карточка + задача, purpose = «кому отдать»

Классы (`id: описание`):
- `agy_flash`: по умолчанию, всегда модель `gemini-3.8-flash-high`. Разведка, чтение, ресерч, логи, прогоны, сборка, тесты, деплой, индексация, ssh-механика, правки по готовой спеке, код по готовой спецификации (файлы, сигнатуры, критерии) без новой логики и дизайна, бойлерплейт. Приёмка по диску и `jev_verify`.
- `основная_сессия`: однострочная правка; HANDOFF, FIXES, README; приёмка; в обычной сессии (без /orc и /super-orc) ещё новая логика, важный код, дизайн, тексты сайта (решение 02.10). В /orc и /super-orc эти четыре идут в `claude_субагенты` (worker по спеке).
- `claude_субагенты`: большой изолированный кусок важной работы, где нужны качество и параллельность. Больше 3 одновременно — сначала строка владельцу.
- `opus`: архитектура, git-археология, плавающий баг, широкий blast radius.
- `manual_review`: креды, оплата, OAuth, субъективный дизайн/копи, бизнес-решения, третьи лица, реальные устройства.

`auto` → сообщить выбор одной строкой, ответа не ждать. Не `auto` → `manual_review` или ближайший класс из дистрибуции, тоже одной строкой.

## 3. После исполнителя

Приёмка: `jev_verify` против диффа или файла на диске. Источники расходятся — `jev_compare`.

## 4. Рекомендация владельцу: модель и усилие основной сессии

Владелец учится выбирать модель на реальных задачах. В начале задачи из 2+ шагов, в /orc и /super-orc всегда, дай 1–3 предложения простыми словами: что стоит сейчас, подходит ли, и короткая причина «потому что …». Модель — строка «powered by the model named …», усилие — строка `reasoning_effort` в системном промпте; нет строки — так и скажи. Работает в обе стороны:
- Дороже нужного → «Сейчас Opus, усилие высокое. Здесь я только пишу задания флешу и проверяю, хватило бы Sonnet со средним усилием».
- Слабее нужного → «Сейчас Sonnet, усилие низкое. Задача про плавающий баг на много файлов, Sonnet легко пойдёт по ложному следу, лучше Opus с высоким усилием».
- Подходит → «Sonnet со средним усилием подходит: правки по готовому плану».

Ориентиры. Sonnet, среднее усилие: оркестровка, приёмка, брифы, правки по плану, тексты по готовому смыслу. Opus или высокое усилие: архитектура, плавающий баг, широкий охват правок, сложный дизайн решения, длинная цепочка рассуждений. Низкое усилие: вопрос-ответ, однострочные правки. Модель посреди работы сама не меняю, только советую на следующий раз. Не хвастаться и не оправдываться.
