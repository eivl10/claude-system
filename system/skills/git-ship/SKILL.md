# git-ship (коротко)

Я сам веду git и GitHub. Без субагентов: 3-4 короткие команды дешевле запуска агента. Вывод держу коротким (`status -sb`, `diff --stat`, `log --oneline -10`), полный diff не читаю без нужды.

## Кого пушу
- **Реестр: `projects.md`** (рядом с этим файлом). Проект из реестра: закончил задачу - коммит и push сам.
- **Не из реестра**: не пушу и репо не создаю, только по прямой просьбе владельца. Локальные коммиты можно.
- В реестр проект вносит владелец («веди этот проект»); я дописываю строку.

## Жёсткие правила
1. Перед любым push: `bash ~/.claude/skills/git-ship/scripts/prepush-scan.sh "<папка>"`. Код 2 = не пушить, показать находки. Код 1 = назвать замечания, пушить можно, если они не про секреты.
2. Push без токена в адресе: `git -c credential.helper= -c credential.helper='!gh auth git-credential' push`. Вход уже сделан через `gh auth`. PAT-токены не запрашивать и не использовать; в чат, файлы, адреса, команды не вставлять. Если владелец прислал токен, не использовать и посоветовать удалить.
3. Только по отдельному «да»: `--force`, удаление веток/тегов/репо, смена репо на public, переписывание истории. Перед необратимым: бэкап `git bundle` и проверка, что файл создан.
4. Новые репо: private, ветка `main`, владелец `eivl10`.
5. Строки про ИИ в коммитах и PR не добавлять (`Co-Authored-By`, «Generated with...»): запрет владельца.
6. Значения секретов не печатать; в адресах скрывать всё до `@`.
7. Без просьбы не делаю: массовый push, замену папок-версий, чистку истории.

## Коммит
1. `git status -sb` и `git diff --stat`.
2. Файлы добавляю по именам, не `git add .`. Не добавляю `.env`, ключи, `node_modules`, сборки, базы.
3. Сообщение одной строкой: `тип: English / по-русски`. Типы: `feat` новое, `fix` починка, `docs` документация, `refactor` перестройка без смены поведения, `chore` прочее. `!` после типа (`feat!:`) = сломана совместимость.
   Пример: `fix: crash on empty file / вылет на пустом файле`
4. Один коммит = одно изменение. Если это починка бага и есть `FIXES.md`, дописать туда.

## Версия (релиз)
1. Последний тег: `git describe --tags --abbrev=0`. Что нового: `git log <тег>..HEAD --oneline`.
2. Номер: есть `!` - +1 к первой цифре; иначе есть `feat` - +1 ко второй; иначе +1 к третьей. Пока первая цифра 0: и `!`, и `feat` дают +1 ко второй. Тегов нет - `v0.1.0`. Предложить номер, дождаться «да».
3. `CHANGELOG.md` (Keep a Changelog): сверху `## [X.Y.Z] - ГГГГ-ММ-ДД`, под ним `### Added / Changed / Fixed`, строки «English / по-русски». Файла нет - создать.
4. Номер версии в файле проекта (`package.json`, `pyproject.toml`, `VERSION`), если есть.
5. Коммит `chore: release vX.Y.Z / релиз vX.Y.Z`, затем `git tag -a vX.Y.Z -m "vX.Y.Z"`, затем push с тегом (`git push --follow-tags`, helper из правила 2).
6. `gh release create vX.Y.Z --notes-file <файл>` только по просьбе. Сборки (exe/zip) кладу в Release, не в git.

## Новый проект в GitHub (по просьбе)
1. `.gitignore` по стеку; секреты в `.env` + `.env.example`.
2. README на двух языках (skill `readme`).
3. `prepush-scan.sh`; `git init -b main`; первый коммит; `git tag v0.1.0`.
4. `gh repo create eivl10/<имя> --private`, `git remote add origin https://github.com/eivl10/<имя>.git`, push с тегами через helper.
5. Добавить строку в `projects.md`.

## Слова
- **коммит** - сохранённый снимок проекта; **push** - отправка коммитов на GitHub; **тег** - закладка версии (`v1.2.0`), вернуться к ней: `git checkout v1.2.0`.
- **номер версии** `1.2.3`: первая цифра растёт при поломке совместимости, вторая при новой функции, третья при починке.
- **тип** (`feat`, `fix`...) - метка в начале сообщения; по ней считается номер версии.
