# logging: журнал вместо догадок

Правило владельца, 15.11.2026: «внедрять логирование на проектах, где есть вероятность ошибок и проект крупный. В проекте Расхламление мы ошибки ловим наугад. Если бы было сразу логирование, было бы проще».

## 1. Нужен ли журнал

Нужен, если проект живёт дольше одной сессии и верно хотя бы одно:
- работает без глаз владельца: бот, сервер, планировщик, парсер, фоновая задача;
- ходит во внешние сервисы: API, Telegram, база, ИИ-модель, почта, оплата;
- обработка идёт в несколько шагов, и сбой одного шага снаружи не виден;
- кода больше пяти файлов или пятисот строк;
- причину бага уже искали наугад. Второй раз наугад не искать.

Не нужен: одноразовый скрипт, статичный сайт, макет, вёрстка без логики.

## 2. Когда ставить

- **Новый проект.** Журнал входит в первую же спеку и в первый рабочий кусок кода, наравне с README. «Добавим потом» не принимается: потом уже ищут наугад.
- **Существующий проект без журнала.** При первом баге, причина которого не видна из вывода: сначала журнал на тот путь, где сбой, воспроизвести, прочитать запись, потом чинить. Заодно общий вход по разделу 3, если его нет. Разметку остального кода предложить владельцу одной строкой «Могу добавить журнал во весь проект», если это больше одного куска работы.
- **Отладка.** Нет записи о сбое — не чинить по догадке и не по тексту ошибки. Добавить запись, повторить сбой, прочитать. Связано с правилом «сначала traceback».

## 3. Минимальный стандарт

1. **Один вход.** Одна настройка журнала на проект, все модули берут её. Своё не писать, брать штатное для стека:
   - Python: `logging` с `RotatingFileHandler`, в ботах на asyncio ещё обработчик ошибок цикла событий;
   - Node: `pino` либо один модуль-обёртка над записью в файл;
   - PowerShell: одна функция `Write-Log` в общем файле;
   - PHP: `error_log` в свой файл либо Monolog, если уже есть Composer.
2. **Куда.** Папка `logs/` в проекте, она в `.gitignore`. Ротация по размеру, например 5 МБ на файл и 5 файлов, чтобы журнал не рос без конца. В Docker дополнительно вывод в stdout, чтобы работал `docker logs`.
3. **Формат.** Одна строка — одно событие: время, уровень, часть программы, событие, ключевые поля. Лучше JSON-строками: их читают `jev_extract` и `jev_classify`.
4. **Сквозная метка.** У одного входящего события один идентификатор на все шаги: сообщение в боте, заказ, запуск планировщика. По нему собирается вся цепочка.
5. **Уровень.** По умолчанию INFO, подробный DEBUG включается переменной окружения без правки кода.
6. **Последний рубеж.** Перехват необработанных ошибок на уровне процесса: `sys.excepthook`, обработчик asyncio, `process.on('uncaughtException')` и `unhandledRejection`, `trap` в PowerShell. Падение без записи — дефект.

## 4. Что писать обязательно

- Старт и остановку: версия или хеш коммита, режим, ключевые настройки без секретов.
- Каждый внешний вызов: куда, сколько длился, чем кончился. При ошибке — код и тело ответа, усечённое.
- Каждую ошибку с полной трассой: `logger.exception` или аналог. Пустой `except: pass` и проглоченный `catch` запрещены: либо запись, либо проброс.
- Развилки логики: какую ветку выбрала программа и по какому признаку. Именно этого не хватает, когда «бот ответил странно».
- Работу с ИИ-моделью: модель, длительность, размер запроса и ответа, начало запроса и ответа, усечённое до пары сотен знаков. При сбое разбора ответа — сырой ответ целиком.
- Повторы и отказы: какая попытка, сколько ждали, почему сдались.

## 5. Чего в журнале быть не должно

Токены, пароли, ключи, куки, строки подключения, номера карт и документов. Чужую переписку и персональные данные целиком не писать: идентификатор и усечённое начало. Если значение может оказаться секретом, маскировать его в общем входе, а не в каждом вызове.

Не писать на уровне INFO внутри горячих циклов: журнал не должен тормозить программу и забивать диск.

## 6. Чтобы владелец мог пользоваться

- В README раздел «Где смотреть журнал»: путь и одна команда PowerShell, которая показывает последние ошибки.
- Для ботов и серверов предложить владельцу сообщение о критической ошибке ему же в Telegram. Это исходящее сообщение, включать только после его «да».
- В FIXES к каждому исправленному багу строка: по какой записи журнала нашли причину. Не нашли по журналу — значит, записи не хватило, добавить её тем же исправлением.

## 7. Кто делает

Что и где записывать — решение основной сессии, идёт в спеку списком мест. Настройка общего входа и расстановка записей по готовому списку — код по спеке, уходит в agy Flash. Приёмка: один прогон с намеренной ошибкой и проверка, что в файле журнала появилась строка с трассой и сквозной меткой.
